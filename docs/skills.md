# Agent Skills interoperability

Semwright supports the open [Agent Skills](https://agentskills.io/) package shape as an
agent-side procedural-knowledge layer. A Skill can teach an agent *when* and *how* to
compose Semwright, but the Skill is not an executable Semwright principal and cannot
grant authority.

The implementation follows four distinct concepts:

```text
Skill             = procedural guidance for an agent
Capability        = typed executable operation
Recipe            = deterministic declarative program over capabilities
Learned Workflow  = observed successful procedure compiled, verified and promoted
```

Do not collapse these concepts. In particular, there is intentionally no
`SourceKind::Skill` and no `skill.execute` capability.

## Current open-standard baseline

The current Agent Skills specification defines a directory containing `SKILL.md`, with
required YAML `name` and `description`, plus optional `scripts/`, `references/` and
`assets/`. Discovery is progressive: clients can inspect name/description first and
load the body/resources only when the Skill is relevant.

Semwright validates the current standard fields, including the canonical Skill-name
constraints. It accepts standard Skills with no Semwright metadata. Semwright additionally
applies bounded package/security limits documented below.

The standard's `allowed-tools` field is currently experimental. Semwright preserves it
as client metadata but never interprets it as a Broker grant.
## Authority boundary

```text
Agent Skill
    |
    v
agent reasoning
    |
    v
Semwright MCP / CLI
    |
    v
Broker -> schema -> policy -> provider
```

Skill text, resource files, provider metadata and application content are all
non-authoritative. They may explain or recommend an operation. Every real operation still
enters the normal Broker path and is independently schema-validated and policy-checked.

A registered/available route is not a permission. `skill doctor` therefore reports
aggregate required scopes as information and may surface the Broker's conservative
`policy_preview` (`allow`, `deny`, `require_confirmation`, or an argument/target-dependent
state). That preview is explicitly non-authoritative: every execution is rechecked by
Broker policy with the real arguments and target, and doctor never manufactures a grant.

## Package layout

A portable Skill remains standard:

```text
my-skill/
├── SKILL.md
├── references/
├── scripts/            # optional, never auto-executed by Semwright
├── assets/             # optional
└── .semwright/         # optional Semwright interoperability metadata
    ├── requirements.json
    ├── lock.json       # optional, generated by skill lock
    └── examples/       # optional objective JSON fixtures
```

`.semwright/requirements.json` is auxiliary, versioned metadata. Removing it leaves a
normal Agent Skill.
## Requirements v1

Requirements can express:

- an exact capability ID, including a promoted `recipe.<slug>.run`;
- a catalog query over text, provider identity, source kind, application, tags and object types;
- required vs optional dependencies;
- a minimum number of query matches;
- a Semwright version requirement;
- reserved semantic-package requirements for future package contracts.

The JSON Schema is `schemas/skill-requirements-v1.json`.

Requirements deliberately contain no permission/grant field. Unknown fields are rejected.
A Skill cannot ask the requirements loader to turn `filesystem.write`, a driver scope,
or any other policy scope into authority.

Semantic-package requirements are syntax-reserved for future contracts such as
`scene/v1`; v1 reports them as not supported rather than pretending to resolve a feature
that Semwright does not yet implement.

## Descriptor locks and drift

`semwright skill lock PATH` resolves the current catalog and writes
`.semwright/lock.json`. The lock records the version reported by the connected
Semwright Broker, plus for each selected capability:

- capability ID and version;
- provider identity and provider version;
- descriptor SHA-256;
- input/output schema SHA-256;
- the digest of the requirements file.

The lock is review/reproducibility evidence, not trust or policy. `doctor` compares
`minimum_version` and lock drift against the connected Broker version (not merely the CLI
build version), and reports drift when the Broker/capability/provider/schema changes or a
locked capability disappears.
## CLI

```sh
semwright skill validate PATH
semwright skill inspect PATH
semwright skill doctor PATH
semwright skill scaffold NAME OUTPUT
semwright skill export CAPABILITY --output OUTPUT
semwright skill test PATH
semwright skill lock PATH
semwright skill bundle PATH OUTPUT.zip
```

### validate

Purely static. It never contacts a Broker. It checks frontmatter, Agent Skills name and
description rules, UTF-8, paths, resource budgets, optional requirements/lock schemas,
symlinks and package integrity. `--json` returns a stable machine-readable report.

### inspect

Shows Skill metadata/resources separately from declared Semwright executable dependencies.
It does not execute the Skill body or scripts.

### doctor

Loads the Skill, then resolves exact/query dependencies through the real
`capabilities.search`/`capabilities.describe` catalog. It pins one catalog revision for
the operation and distinguishes:

- missing capability;
- registered capability with unavailable route;
- descriptor/schema/provider drift.

Policy grants are intentionally not inferred from availability.
### scaffold

Creates a minimal standard Skill and empty optional requirements file. The output directory
name must match the Skill name. It does not install, register or trust the Skill.

### export

Describes one live capability (including a promoted Recipe capability) and generates a
small starter Skill with an exact requirement plus a descriptor snapshot under
`references/`. Generated text says that it is a starter; it does not invent business
criteria absent from the capability.

### test

Checks objective properties only: static package validity, requirement resolution, route
availability, descriptor drift, and optional `.semwright/examples/*.json` against current
capability input/output schemas. It executes zero application operations and zero Skill
scripts.

### bundle

Produces a deterministic stored ZIP whose entries all live beneath exactly one top-level
Skill directory. It rejects traversal/symlinks and excludes known VCS/build/cache paths.
A conservative filename heuristic excludes common credential/key files. That heuristic is
defense in depth, not a proof that a bundle contains no secrets.

## Security model

Semwright treats third-party Skills as untrusted user-level instructions.

- **Malicious instructions:** Broker policy still wins.
- **Malicious scripts:** Semwright never auto-executes `scripts/`.
- **Traversal/absolute paths:** rejected by the package/archive path validator; backslashes and Windows drive prefixes are rejected rather than rewritten into a different archive identity.
- **Symlinks/hardlinks/races:** symlinks are rejected; on Unix, multiply-linked package files are also rejected. Bounded reads re-check package containment and open-file identity, and lock updates replace the package entry instead of truncating an externally linked inode.
- **Resource bombs:** file count, size, depth and total-package budgets are enforced.
- **YAML/JSON ambiguity:** frontmatter is bounded; YAML anchors, aliases, custom tags and duplicate top-level fields are rejected. Semwright requirements/lock JSON rejects duplicate object keys recursively.
- **Secrets:** bundle excludes common secret/key filenames without reading or logging their contents.
- **Prompt injection:** Skill/application text never changes message priority or Broker policy.

Current budgets are deliberately conservative: 1 MiB `SKILL.md`, 64 KiB frontmatter,
500 supporting package entries (files/directories), 25 MiB per resource file, 50 MiB total package size and directory depth 16.
They are Semwright safety budgets, not new requirements of the open standard.
## MCP, CLI and clients

The Skill lives primarily on the agent side. With MCP, a Skill should teach an agent to use
Semwright's small discovery/gateway surface; Semwright does not parse the Markdown and
automatically run a workflow.

The same Skill can teach a shell-capable agent to use the CLI. Semwright remains
transport-independent.

OpenAI ChatGPT/Codex and Anthropic Claude can consume the standard Skill shape according to
their current client/runtime support. Vendor-specific UI/install behavior is intentionally
not encoded here. Compatibility claims should distinguish:

1. static standard validation;
2. Semwright dependency compatibility;
3. integration-tested client behavior;
4. live application testing.

Passing level 1 or 2 is not evidence for level 4.

For a generic Agent Skills client, install or expose the standard Skill directory using that
client's supported mechanism, then expose Semwright separately through MCP or the CLI. The
Skill's discovery metadata tells the agent when to load its body; the Semwright catalog
still tells it what executable operations actually exist.

For ChatGPT/Codex, use the current OpenAI Skills/plugin installation surface for the standard
Skill package and configure Semwright as its own execution/tool connection. A plugin may
bundle Skill guidance and connected tools, but installing guidance does not bypass provider
authentication, workspace policy, or Semwright Broker policy.

For Claude, use the current custom Agent Skills mechanism (Claude Code/API/claude.ai as
applicable) and provide Semwright separately through MCP or shell/CLI. Claude runtimes may
execute bundled Skill scripts in their own environment; that does not change Semwright's v1
rule that the Semwright Skills layer itself never auto-executes `scripts/`.

## Skill-guided provenance

V1 deliberately does **not** add Skill identity to Broker/session semantics. Doing so only
for this feature would couple an agent-side instructional artifact to the trusted execution
protocol and would risk making provenance look like authority.

A future client may attach an explicitly untrusted annotation such as Skill name plus
package/version digest to an execution trace. That metadata must remain informational and
must never influence policy, provider selection, approval, or promotion gates. This would
support questions such as “which repeated workflows emerged while Skill X was in use?”
without creating a privileged Skill principal.

## Future publication, signatures and Conformance Cloud

Portable bundles currently expose a deterministic SHA-256. That is integrity evidence, not
a trust verdict. The package/report models intentionally leave room for future publisher,
signature, provenance and certification metadata, but v1 does not invent a PKI or claim that
a signed Skill's instructions are safe.

`validate`, `doctor` and `test` reports use versioned machine-readable shapes suitable for
future upload to a Semwright Conformance Cloud. This repository does not implement hosted
Skill storage, marketplace search, ratings, payments or cloud certification in this pass.

## Workflow Distillation

The supported compilation path is:

```text
Skill guidance
    -> normal Semwright executions
    -> successful traces
    -> repeated deterministic pattern
    -> candidate Recipe
    -> static verify
    -> successful replay
    -> promoted recipe.<slug>.run capability
```

Markdown is never parsed magically into a Recipe. Distillation learns from actual Semwright
execution traces. Promotion currently requires static verification and at least one
successful replay.

This creates progressive compilation: early Skills can contain more procedural guidance;
after stable procedures are promoted, the Skill can shrink toward reasoning about **when**
and exceptions while delegating **how** to verified capabilities. Semwright never rewrites
a user's Skill automatically.
## First-party Skills

The repository ships a small curated set under `skills/`:

- `semwright-core`: DISCOVER → DESCRIBE → INSPECT → EXECUTE → VERIFY.
- `semwright-cross-app-artifacts`: producer/consumer tags, broker-mediated handoff and destination verification.
- `semwright-workflow-distillation`: record/compile/verify/replay/promote.
- `semwright-driver-authoring`: semantic first-party driver design, security and conformance.
- `semwright-figma-production`: current first-party Figma driver workflow, artifact tokens and limitations.

Each Skill keeps `SKILL.md` small and moves detail to `references/`.

## Figma proof

The Figma Skill is derived from the current first-party driver, whose production route is
Broker/policy -> sandboxed driver -> authenticated loopback bridge -> official Figma Plugin
API, with a separate protected official REST route.

Its requirements reference real current `driver.figma.*` capabilities. Exported Figma
artifact tokens remain provider-owned handles; the Skill explicitly does not relabel them
as filesystem paths.

Repository fake-host/sandbox tests are not described as real-Figma certification.

## Conformance evidence

The Skills crate contains unit, negative/security and property tests for parsing, UTF-8,
frontmatter, requirements, traversal, symlink escape/loops, resource budgets, drift,
schema examples, scaffold/export and deterministic bundles.

On 2026-09-27 all five first-party Skills were also checked with the open standard's
reference `skills-ref validate` command from `agentskills/agentskills` commit
`69ef37e9424c0a7ea9dd2293b559e43ec8176379`; all five reported `Valid skill`. This is
static format evidence only. The reference project describes `skills-ref` as a demonstration
library, so Semwright does not elevate that result into a trust or live-client claim.

The core integration suite also loads the official Workflow Distillation Skill, represents
a deterministic Skill-guided operation sequence through the fake Broker, compiles it,
verifies it, replays it, promotes it and asserts Recipe provenance.

Fuzz targets cover Skill/frontmatter loading, requirements loading and archive path
sanitization. Heavy fuzzing and full workspace/coverage matrices belong in hosted CI on
this repository because local development environments may be disk-constrained.
