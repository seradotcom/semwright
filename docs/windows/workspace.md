# Windows filesystem workspaces

The owner configures named roots in the daemon's configuration. MCP and CLI clients
use the same policy and native filesystem backend; choosing another interface does
not grant access to another directory.

Use an existing ordinary absolute drive path. For example:

```toml
[policy]
profile = "observe"

[[policy.filesystem]]
name = "project"
path = 'D:\Projects\Example'
read = true
write = true
```

Keep this configuration outside the granted project. The daemon rejects roots that
contain, or are contained by, its configuration, runtime or state. Windows returns
a `\\?\` prefix when resolving paths internally; do not copy that device spelling
into the grant. UNC/device paths, junctions and other reparse points are not
supported grant roots. Case variants and short DOS names are resolved before checking
protected-root overlap. The native backend opens each root component relative to an
already opened directory handle, refusing reparse points along the way.

On Windows, a bounded semantic snapshot may select a live window with
`ui.snapshot` and a `ref` returned by `window.list` in the same broker session.
Core verifies the reference and Windows scopes the UIA tree to that HWND.
An `app` filter without a ref is rejected on Windows because this backend cannot
enforce it; do not substitute a desktop-wide snapshot. UI snapshots never
authorize mutation.

Start the foreground broker with the reviewed configuration, then use the MCP
snippet generated by `semwright setup` in a compatible client. The existing
`filesystem.read` and `filesystem.write` commands take the root's name and a relative
path. Reads return UTF-8 text. Writes atomically replace bounded text files. Both
operations enforce the declared read/write authority; a write grant does not grant
an unrestricted shell or permission to execute a project's scripts.

For a binary transfer between two separately granted roots, use
`artifact.handoff` with `overwrite=false` and a matching `expected_sha256`. On
Windows, the native backend publishes the new file with a handle-relative,
atomic no-replace rename. If the destination already exists, the request
returns a conflict instead of replacing its bytes. A lost response still
requires checking the destination before attempting any further action.
This protects a new-only publication, not an edit to a preexisting file:
`filesystem.write` still replaces files and does not offer compare-and-swap.

For Project Graph assets backed by an explicitly readable Windows root, native
file observation now records a volume/file-index/creation-time instance identity
and checks last-write/change-time and size before and after a bounded read.
It reopens the same name under the pinned directory handle to detect replacement.
A different file at that name is ambiguous until explicitly rebound by the owner;
normal in-place changes can be recorded as new revisions. This is best-effort
revalidation, not an atomic transaction, lock or permission to overwrite files.

### Windows initial-process attestation

Windows sandbox children now remain suspended until Core has verified both
membership in the exact assigned kernel Job and the newly created process
token: current owner SID, requested AppContainer SID, LPAC status and exact
capability SID/attribute set. A mismatch terminates the child and its Job
before untrusted instructions run, and records a bounded diagnostic. This
also applies to existing Windows drivers; it grants no new application
capability. A successful attestation proves containment before ResumeThread,
not successful Blender startup or native Save/Reopen.

### Native Blender runtime preparation

The Windows platform layer has a Host-internal, owner-pinned Blender 5.2.1
runtime snapshot primitive. A trusted Host caller must first validate a separate
owner grant for the executable and the read/execute runtime directory, a fresh
private destination, and nonoverlap with the writable project and private state.
Preparation copies bounded files from non-reparse, identity-checked handles,
checks trusted ACLs and each file digest, verifies the exact sealed Blender
executable, and returns a runtime inventory. Cancellation and existing
destinations fail without treating the operation as an application launch.

The platform now also has a Windows-only, Host-mediated closed launch mode.
It accepts exactly the pinned Blender executable under the immutable runtime,
a fixed headless/bootstrap argument list, one write-enabled workspace mount,
one read-only bootstrap mount, one read-only executable runtime mount, no
network or GPU, native x64 and a one-process Job limit. It injects only
first-party Blender runtime environment values and registryRead (read-only)
to allow Windows application initialization. The initial process must
already pass exact Job, owner SID, AppContainer, LPAC and capability attestation
before resume. Executable validation uses the already separate 512 MiB
application limit, without widening the 64 MiB generic sealed-driver limit.

This platform primitive alone does not enable driver.blender.* on Windows.
Driver manifests can now express the closed windows_native_profile request for
blender_5_2_1_initial on their exact blender sealed tool. The request accepts
only workspace and blender-runtime mounts, without dependencies, system config,
NVIDIA, or per-tool resources. It does not grant permission.

The owner config driver_windows_blender52_initial defaults false, independent of
network, recovery and GPU settings. Driver Host denies requests without the
owner grant. Under explicit owner opt-in and separate grants for the exact
Blender executable, entire read-only runtime and writable workspace, it can
prepare a private snapshot and a fixed first-party bootstrap and request the
closed platform launch. The generic sealed-tool path has no Blender fallback;
the native session rejects driver-supplied arguments and CWD. Preparation is
bounded, cancellable, hashed and separate from the driver process. The child
uses a nonce-bound readiness marker with a bounded timeout and owner-process
cleanup on failure. Fixed source assets are pinned to first-party donor commit
a63deb7a542876af0656b4b398ff5463ad6c5ee5, not resolved from user scripts.

Platform compilation and simulated/negative tests are not proof of an
installed Blender 5.2.1 running under the broker. Physical scene Save/Reopen
in an independent process, input mutation/readback and release admission
still require separate evidence. The Linux Blender 4.5.14 LTS profile retains
its own evidence and is not qualified by these Windows preparation tests.

Requests outside the root, nested junction escapes, alternate data streams and
hard-linked files are rejected by the native backend. Do not retry a denied request
through another provider. For a completed edit, inspect the returned result and read
the file back; process exit alone does not prove its contents.

Owner policy is loaded at broker startup. After changing a grant, restart the
broker. Reconnecting a client does not restore a removed grant. Existing results
remain observations, not permission to repeat an earlier write.

## Focused Windows verification

The `Windows workspace connection` workflow builds native Windows binaries and
checks configuration-to-backend compatibility, protected-root overlap and junction
rejection. Its stdio MCP smoke starts the real broker, reads and edits a disposable
project, reads back the change, reconnects for a second task, and checks rejection
after write authority is removed and the broker restarts.

Run the same bounded smoke with matching binaries:

```powershell
python scripts/windows/workspace-smoke.py --bin-dir target/debug --output verification/windows-workspace
```

The result is native broker/MCP protocol evidence. It does not establish acceptance
in a third-party agent host, interactive desktop control, unrestricted process
confinement, or a signed/public release.
