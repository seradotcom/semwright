# Secondary runtime tools

Semwright treats application runtimes and helper executables as explicit owner-granted tools, never as ambient programs discovered from PATH or platform install conventions.

For one-shot tools, drivers should call `DriverExecutionContext::execute_runtime_tool`. The SDK selects the platform-safe route by negotiated protocol: Linux v4 can consume a Host-materialized sealed executable, while protocol v5 uses Host mediation on Linux and Windows. Callers use a logical tool name rather than an installation path.

Portable runtimes may also require a read-only runtime directory for libraries/resources. That directory remains a separately named mount; executable authority stays in `Manifest.tools` and is SHA-256 pinned.

Protocol v5 adds an optional per-tool workspace allowlist and a logical working directory. The working directory is the root of one declared workspace mount; nested relative paths are deliberately rejected until every platform can resolve them without symlink/reparse races. On Windows, Driver Host constructs a short-lived AppContainer child with only the workspace mounts named by that tool and keeps the resolved working-directory path host-only.

macOS exposes the same digest/ownership/native-architecture verification entry point for secondary tools, with a distinct 256 MiB tool budget, but arbitrary driver/plugin sandbox execution remains fail-closed. Verification alone is not runtime-tool acceptance on macOS.

Linux protocol v4 keeps the compatibility path that materializes sealed tools inside the driver sandbox. Protocol v5 switches Linux to Host-mediated invocation: Driver Host stages the verified tool separately, launches a short-lived nested sandbox, and grants only the workspace mounts listed for that tool. Windows v5 provides the same logical per-tool mount contract through Host-mediated AppContainer execution. macOS executable verification exists, but arbitrary driver/plugin sandbox execution remains fail-closed, so this document does not claim macOS runtime-tool acceptance.

Godot is the first production consumer of the v5 one-shot boundary: its runner requests the logical `godot` tool through Driver Host and production configuration resolves project/output/secret authority by logical grant names. This demonstrates the generic path without implying that real Godot acceptance has been certified on every host OS.

Protocol v6 adds detached Host-owned runtime-tool jobs for work that intentionally outlives the `Execute` request that starts it. Start returns an opaque Host-generated job ID; status and cancellation are accepted only from the same driver session that created the job. A provider may retain at most eight jobs, terminal results are collected on the first successful status read, and closing the driver transport cancels every retained job. Detached jobs keep the v5 tool/mount allowlist, have a bounded one-hour wall deadline, and remain unsupported when the manifest requests aggregate per-operation CPU accounting that the platform cannot prove.

Protocol v7 adds typed runtime-tool arguments. `MountPath` identifies only the root of an already-delegated workspace mount and `ToolPath` identifies only a separately owner-pinned dependency listed by the primary tool contract. The driver never receives owner installation paths: Driver Host validates the logical references and each platform expands them only after its child mounts/tools have been materialized. Linux exposes a selected dependency from the same sealed memfd bytes; Windows copies and re-attests only selected dependencies inside the tool child's AppContainer profile. `ToolPath` guarantees materialization and path authority, not permission for the primary tool to spawn a descendant: the current Windows sandbox deliberately denies driver child-process creation, so Windows conformance verifies that the dependency is the readable re-attested PE rather than weakening that policy. Raw v4-v6 arguments cannot forge the reserved Host placeholder format. Nested relative mount paths remain intentionally unsupported until Linux and Windows have equivalent handle-relative/reparse-safe resolution.

Protocol v8 adds per-tool system-config allowlists. A tool may name only roots already declared in `Manifest.system_config`, and Driver Host reconstructs only those read-only/non-executable config mounts in the child rather than inheriting every config visible to the driver. Linux preserves the declared `/etc/<child>` destination; Windows preserves the same logical `system_config` identity in the AppContainer mount table while materializing the owner-granted native path. Secrets, network and loopback authority are still never inherited by a tool child.

Protocol v8 also adds provider-scoped persistent runtime-tool sessions for application runtimes that must survive across multiple Execute requests. Start is authorized by an active request, but the resulting opaque handle belongs to that DriverProvider rather than to the caller's user-session string; a later request through the same provider may exchange a bounded frame or close the session. This is intentionally different from protocol-v6 jobs, which remain user-session scoped. Driver Host owns the process, permits at most two persistent sessions per provider, bounds frames to 256 KiB and lifetime to one hour, reaps a session on framing/timeout failure, and reaps every remaining session when the provider disconnects. Session close remains available as cleanup after request cancellation. The current protocol uses a length-prefixed stdin/stdout channel intended for a Semwright-owned runtime wrapper; native application IPC can remain behind that wrapper. Linux and Windows receive native conformance coverage; macOS remains fail-closed for execution until a supported platform isolation primitive exists. Aggregate per-operation CPU accounting remains unsupported for persistent sessions rather than being approximated.

## Runtime migration status in this integration candidate

| Driver/runtime | Lifetime / shape | Production runtime authority | Status |
| --- | --- | --- | --- |
| Blender | Persistent background application session | Protocol-v8 provider-scoped Host session; sealed Blender dependency behind the Host-owned session runner | migrated; no production driver `tool_path()` or private process launcher |
| LibreOffice | Persistent soffice + UNO/Python bridge | Protocol-v8 provider-scoped Host session with per-tool system-config allowlists and sealed runtime dependencies | migrated; no production fixed `/usr/bin` launcher paths |
| MLT | Render/probe work may outlive the initiating request | Typed Host tool arguments plus Host-owned detached render jobs; runtime bundle entrypoints are contained and byte-matched to sealed dependencies | migrated; no production `runtime.json` resolver |
| Motion Canvas | Async render job with Node helper + browser | Host-owned detached jobs, typed mount paths, SHA-pinned Node tool, embedded render helper and explicit runtime bundle | migrated; no production `runtime.json` resolver |
| Godot runner | Request-scoped one-shot tool | Protocol-v5+ Host-mediated tool boundary with logical mounts | migrated |

Persistent sessions and detached jobs are intentionally not emulated with request-scoped `execute_runtime_tool`: doing so would change cancellation and lifetime semantics. Protocol v6 provides session-bound detached jobs; protocol v8 provides provider-scoped persistent sessions. Both reuse the same logical tool/mount/dependency authority rather than adding per-driver path resolvers.

Built-in platform backends are a separate execution boundary, not fake Driver Host providers, but they follow the same no-ambient-discovery rule. Linux `app.launch` accepts only owner-configured canonical absolute executables with an exact lowercase SHA-256 and re-verifies the application bytes before every launch. The Linux built-in Chromium backend is disabled until an owner supplies the same path+digest pair; it does not assume `/usr/bin/chromium` or search `PATH`. Chromium additionally owns a disposable profile and loopback CDP endpoint. macOS and Windows currently do not register those two launch surfaces and reject configured application/Chromium launch rather than silently ignoring it.

Application executables have a separate 512 MiB verification budget because real application binaries may exceed provider and secondary-tool budgets. That changes only verification capacity; it does not grant execution or imply sandbox support. Platform format/architecture and ownership checks remain platform-specific.

The remaining platform gap is macOS execution of arbitrary Host-mediated secondary tools. macOS verifies secondary-tool digest, ownership and native architecture through the shared verifier, but execution remains fail-closed until Semwright has a supported platform isolation primitive with equivalent guarantees. This candidate does not treat verification as runtime-tool acceptance on macOS.

`scripts/verify-driver-runtime-tools.py` is a zero-baseline ratchet for production first-party driver sources (including `integrations/*/driver/src`) and built-in adapter sources. It rejects embedded common OS installation paths, ambient `which`/`command -v` discovery, direct driver `tool_path()`, private `runtime.json` resolvers and `/plugin/tools/` assumptions; there are no tolerated production exceptions. Test fixtures, developer scripts and explicitly bounded compatibility backends remain outside that production resolver guard.
